# Semester Audit Import

Audit version 1.0 is frozen after Phase 2. The parser dispatches by `(kind, schema_version)`; an unsupported pair fails validation. YAML (`.yaml`, `.yml`) uses `yaml.safe_load`; JSON uses the standard JSON parser. Both validate through the same strict Pydantic model with unknown fields forbidden. Dates and times use typed values, the semester timezone uses an IANA name, and every imported entity has a stable ID. IDs are unique across one audit; course parents and schedule/assessment references must resolve within that audit. The fictional example is not real university data.

## Identity And Revisions

The original file SHA-256 is calculated from unchanged source bytes. The canonical content SHA-256 is calculated from validated model content: serialize with Pydantic JSON mode including defaults, sort courses and each course's stable-ID collections by `stable_id`, sort unknown-text lists, then serialize as UTF-8 JSON with sorted object keys, compact separators (`,` and `:`), Unicode preserved, and non-finite numbers forbidden. Array order is preserved for other collections. Thus harmless YAML formatting and equivalent YAML/JSON yield one canonical hash. Audit ID and provenance are included in semantic content.

An already imported canonical hash returns `ALREADY_IMPORTED` without a new revision or archive copy. A different hash for the same semester gets the next revision number. Prior `SemesterAudit` rows and original copies remain. Missing entities in a later audit remain in the database. Audit-derived current facts point to the revision and source that last created or changed them. The archived audit captures the full earlier snapshot; no event-sourcing framework is used.

## Reconciliation

Phase 4D1 adds optional exact human reconciliation. The safe default below is unchanged. Supply `audit-import AUDIT --dry-run --resolution RESOLUTION` to inspect decisions and `audit-import AUDIT --resolution RESOLUTION` to apply them. Both YAML and JSON resolution files are supported. The file is a strict `schema_version: "1.0"`, `kind: semester_audit_resolution` object with `semester`, `audit_id`, `candidate_canonical_sha256`, and a nonempty `resolutions` list. Each decision has `entity_type`, `stable_id`, `expected_current_fact_sha256`, `proposed_fact_sha256`, `expected_current_revision_id`, `action: ACCEPT_REPLACEMENT`, a nonblank `reason`, `actor: MANUAL_USER`, and a timezone-aware `decided_at`. Duplicate decisions and unsupported fields or actions fail validation. `KEEP_CURRENT`, `--force`, and deletion are not supported.

The fact SHA-256 is UTF-8 SHA-256 of compact, sorted-key JSON containing `entity_type`, `stable_id`, the full parsed serialized fact payload, and `information_status`. This binds status and payload provenance as represented by the existing planner. The current record's separate status must agree with its serialized payload. The resolution candidate hash uses the audit canonical hash described above. Resolution canonical SHA-256 uses validated model content with decisions sorted by `(entity_type, stable_id)`; raw SHA-256 uses the exact source bytes. A wrong candidate, semester, audit ID, fact identity, or current revision fails closed. A resolution for `CREATE`, `NO_CHANGE`, ordinary `UPDATE`, an unmanaged row, or an entity-type collision is rejected as extraneous. Only changed, audit-managed facts that would otherwise be `CONFLICT` can become `RESOLVED_UPDATE`; this includes an explicitly approved lower-confidence changed fact. The proposed audit's status is written unchanged. Known-to-`UNKNOWN` remains the historical `NO_CHANGE` policy and is not resolvable in this phase.

An incomplete decision set leaves unresolved `CONFLICT` actions and blocks the entire revision. Real import replans under the project writer lock and inside one DB transaction; a dry-run is diagnostic and its result may become stale before import. On success, each accepted replacement has an `audit_resolution_records` row holding old/new hashes and payloads, previous/new revision IDs, reason, actor, decision time, and manifest raw/canonical hashes. Exact resolution bytes are copied beside the accepted audit with a collision-safe companion name; neither source file is moved. Failed writes remove both new copies. Earlier audit revisions and accepted files remain. Replaying an imported candidate returns `ALREADY_IMPORTED` without another revision, decision row, or archive. CLI exit code 2 remains a blocking conflict; validation or stale-resolution errors exit 1.

`audit-import PATH --dry-run` validates and reports `CREATE`, `UPDATE`, `NO_CHANGE`, `CONFLICT`, or `ALREADY_IMPORTED` without database writes or accepted-file copies. With an exact resolution it also reports `RESOLVED_UPDATE`. The real command repeats the plan in a transaction. New facts are created; UNKNOWN to known is updated. Identical facts are unchanged. UNKNOWN never replaces known. Confidence precedence is CONFIRMED > OBSERVED > INFERRED > UNKNOWN. Without explicit resolution, a changed lower-confidence fact or a changed same/higher-confidence known fact is a blocking conflict. A conflict prevents the entire revision from being committed; existing values stay.

Date-only deadlines retain an `is_date_only` flag. Their database `due_at` uses midnight as a storage marker in the semester timezone, not as a claimed due time. A missing date stays null; no 23:59 or other user-facing time is inferred.

## Files And Transactions

Successful imports copy original bytes to `imports/semester_audits/accepted/<semester_id>/` with a collision-safe name. The source file is never moved or deleted. Validation failures copy the original into `imports/semester_audits/rejected/` with an adjacent text report; no semester data is persisted. Blocking conflicts do not archive as accepted and do not write database data. The copy is prepared during the database transaction and removed if persistence raises. The import plan and writes share one transaction. These roots are configurable.

Use `uniflow init` before importing; it upgrades the configured database to Alembic HEAD. Existing Phase 1 databases without `alembic_version` are stamped at the original revision and upgraded with explicit Phase 2 operations. `uniflow doctor` checks configured directories and database access.
